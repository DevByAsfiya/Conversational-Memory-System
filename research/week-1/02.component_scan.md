# Week 1 : Privacy, Safety, and Isolation - Component Scan

## Why this component this week
This week targets component 10, Privacy, Safety, and Isolation, covering requirements
R16 (per-user isolation), R17 (sensitive-data admission), and R18 (integrity against
injection), plus the deletion requirement R4. This is the highest-priority component
because it has no baseline paper in the handbook, it maps to non-negotiable evaluation
gates (isolation and deletion), and it addresses constructed failures X3 (cross-user
leakage) and X4 (sensitive-data admission) from Deliverable 1. It is currently marked
"gap" in the research landscape.

## Sources glimpsed

**Machine unlearning for LLMs (survey).** Zhang et al., A Comprehensive Survey of LLM
Unlearning, 2025. https://arxiv.org/abs/2503.01854
Mechanism offered: techniques to remove the influence of specific training data from a
model's weights without full retraining (gradient ascent on a forget set, fine-tuning
toward a refusal state, preference-based methods).
Relevance: addresses the "right to be forgotten" (GDPR, EU AI Act), which maps to my
deletion requirement R4. Needs examination for whether it applies to my architecture.

**When Machine Unlearning Meets RAG.** (Noted from search; to glance at.)
Relevance: closest work to my case, since it concerns external retrieval memory rather
than pure model weights. Worth a short check to confirm it does not change the deletion
conclusion.

**FAISS: Billion-scale Similarity Search with GPUs.** Johnson, Douze, Jegou, 2017.
https://arxiv.org/abs/1702.08734
Mechanism offered: the IVFADC index partitions vectors into inverted lists via a coarse
quantizer, and a query scans only a selected subset of lists rather than the whole
database (§2).
Relevance: shows that restricting a search to a subset is structural to the index, which
is the basis for filtering. But the partitioning is by geometric similarity, not by owner,
so it does not itself provide isolation.

**HNSW: Efficient and Robust ANN Search using Hierarchical NSW Graphs.** Malkov, Yashunin, 2018.
https://arxiv.org/abs/1603.09320
Mechanism offered: a graph-based index where nodes are linked to nearby nodes; search
walks the graph from a shared top-layer entry point (§4). Per-element link overhead is
about 60 to 450 bytes (§4.2.3).
Relevance: relevant to both isolation and deletion. The graph deliberately links
semantically similar nodes, and lists element removal as unsupported (§6), which bears
directly on R16 and R4.

**Microsoft Presidio (open-source PII detection framework).**
https://github.com/microsoft/presidio
Mechanism offered: combines regex-based recognisers with a spaCy NER backend, via a
plugin architecture that allows custom entity types. An anonymiser module supports
redaction, masking, hashing, and encryption.
Relevance: directly addresses R17. The plugin architecture matters, because credentials
and API keys are not standard PII entities and would need custom recognisers.
Source type: practitioner tooling and documentation, not peer-reviewed.

**PII redaction pipeline practice (LangChain LLM Gateway redaction docs; Wavect,
"PII Redaction for LLM Prompts", 2026).**
https://docs.langchain.com/langsmith/llm-gateway-redaction
https://wavect.io/blog/pii-redaction-before-llm-prompts/
Mechanism offered: a deterministic gateway placed before any path that could receive
sensitive text, using rules plus a contextual detector, replacing values with typed
placeholders. LangChain's implementation detects API keys, tokens, and credentials
across provider formats, in addition to named entities via Presidio.
Relevance: confirms the architectural pattern (detect at the boundary, before storage)
and that credential detection is treated separately from named-entity PII.
Source type: practitioner documentation.

**Liu et al., Learning to Refuse: Towards Mitigating Privacy Risks in LLMs, 2024.**
https://arxiv.org/abs/2407.10058
Mechanism offered: NAUF, a name-aware unlearning method. Not applicable, since it
operates on model weights (same category as Idea 1).
Relevance: two transferable parts only. §2.2 operationalises detection of whether
sensitive information about a specific entity is present. The Limitations section states
that fine-grained protection is unsolved: the method cannot distinguish harmful from
benign facts about the same individual.


## Mechanisms found and first-pass relevance

**Unlearning (removal from weights).** The survey's own motivation makes clear that
unlearning exists because problematic data becomes absorbed into model parameters during
training, where it cannot be simply deleted and full retraining is prohibitively costly.
First-pass judgment: likely NOT applicable, because my memory is stored externally, not
in the model's weights. Flagged for full evaluation and a probable reject.

**Subset-restricted search (FAISS IVF).** The index natively scans only part of the
database per query, so filtering a search to a subset is architecturally normal. However,
FAISS groups vectors by similarity, so two users' similar memories land in the same
inverted list. Isolation therefore cannot rely on the index's own partitioning; it needs
a separate filter by owner. First-pass judgment: relevant, carry to evaluation.

**Graph-index deletion difficulty (HNSW).** Insertion modifies neighbouring nodes' links
and prunes full nodes (§4), so every node participates in routing paths for others.
Removing a node can strand other nodes and degrade recall, which is why the paper lists
removal as future work (§6). First-pass judgment: relevant to R4, gives deletion an honest
caveat. Carry to evaluation.

**Hybrid detection at admission (rules plus contextual NER).** The consensus practitioner
pattern is a deterministic filter at the boundary combining pattern matching for
structured secrets (keys, tokens, connection strings) with a learned NER model for
unstructured personal data. Directly maps to R17. First-pass judgment: relevant, carry
to evaluation, but requires testing on my own paste patterns.

**Fine-grained detection is unsolved.** Liu et al. state that their approach cannot
distinguish harmful from benign facts about the same entity, and practitioner sources
state that no tool guarantees complete detection. This is the core difficulty for my
domain, where a pasted config file contains benign settings and live credentials on
adjacent lines.

**Integrity against injected content (R18).** No dedicated source scanned this week.
The known statement of the risk is Generative Agents §8.2, which reports that a crafted
conversation could convince an agent of a past event that never occurred. The admission
filter proposed in Idea 3 addresses secrets, not deliberately poisoned content, since
poisoned content need not match any sensitive pattern. Judgment: the storage-side half
of R18 is not addressed by the mechanisms found this week, and the retrieval-side half
belongs to component 7 (context construction), scheduled for a later week. Deferred.

## Shortlisted for evaluation
1. Machine unlearning as a deletion mechanism (R4) - carried to the evaluation matrix,
   expected reject, because it targets parametric memory.
2. Metadata filtering by owner ID for isolation (R16), grounded in FAISS/HNSW subset-search
   capability. Expected adopt.
3. Hybrid PII and secret detection at admission (R17), using rules plus contextual NER.
   Expected prototype, since reliability depends on my own data.

Dropped from further study at scan stage: the detailed unlearning method families
(gradient ascent, preference optimization, etc.), because the category is ruled out at
the architecture level and a deeper read would not change the decision.

# Week 1 - Idea Evaluation Matrix

## Idea 1: Machine unlearning as a deletion mechanism

**Source and citation:** Zhang et al., A Comprehensive Survey of LLM Unlearning, 2025.
https://arxiv.org/abs/2503.01854

**Problem addressed:** Removing the influence of specific data (personal, copyrighted,
or harmful) from a trained model, while preserving general performance and without full
retraining.

**Mechanism:** Adjust the weights of an already-trained model so the target data (the
"forget set") stops influencing outputs, while a "retain set" and general world knowledge
are preserved. Achieved through training-like procedures rather than deletion, because the
data is diffused across the parameters and has no single location to remove.

**Evidence reported by the source:** As a survey, it catalogs methods and their reported
trade-offs rather than presenting one result. It documents two consistent risk categories:
utility degradation (the model gets generally worse) and catastrophic forgetting (removing
one item damages related knowledge).

**Assumptions and limitations:** Assumes the data to be removed lives in the model's
weights, absorbed during training. Its cost and difficulty exist precisely because
parametric memory cannot be edited directly. Success is hard to guarantee and is measured
against the risk of collateral damage to retained knowledge.

**Component and failure mode affected:** Component 10, deletion requirement R4. Related
to the "right to be forgotten" the survey cites as motivation.

**Current approach:** Store memories in an external database, separate from the model.

**Proposed change:** None. Adopting unlearning would mean placing user memories into the
model's weights and then paying to remove them, which introduces the exact problem the
survey describes.

**Expected benefit:** None for my architecture. The legal requirement unlearning is
motivated by (deletion on request) is already satisfied by external storage.

**Integration and operational cost:** Very high if adopted, since it would require
fine-tuning user data into the model and running an unlearning procedure per deletion
request. By contrast, external deletion is a single database operation.

**Security, privacy, reliability implications:** Unlearning carries a risk of utility
degradation and catastrophic forgetting. External deletion carries neither, since removing
a record cannot degrade the model's general ability.

**Does the evidence transfer?** No. The evidence concerns removal from parametric memory.
My memory is non-parametric, so the difficulty the research addresses does not arise.

**Would something simpler work?** Yes. A database delete achieves the required outcome
(the memory is gone and no longer retrievable) at negligible cost, satisfying R4 and the
"right to be forgotten" directly.

**Decision: REJECT.** Unlearning solves removal from model weights. My architecture keeps
memory external and therefore deletable by ordinary operations, so unlearning addresses a
problem my design avoids. This also yields a design principle: do not fine-tune user
memories into the model, as doing so would forfeit trivial deletion and incur unlearning's
cost and risks.

**Revisit condition:** Reconsider only if the design ever moves user memory into model
parameters (for example, personalization via fine-tuning). While memory remains external,
this decision stands.

**Note added after storage-layer read:** external storage makes deletion a database
operation at the logical level, which stands. However, if the vector index is graph-based
(HNSW), physical removal from the index is not immediate (§6, removal listed as
unsupported; typically handled by soft-delete plus periodic rebuild). So the correct claim
is: deletion from the logical store is trivial and immediate; deletion from the retrieval
path is immediate via filtering; physical removal from a graph index may require a rebuild.
This refines rather than overturns the reject of unlearning.

## Idea 2: Metadata filtering by owner ID for per-user isolation

**Source and citation:** FAISS [10], Johnson et al. 2017, https://arxiv.org/abs/1702.08734
(§2, subset-restricted search). HNSW [11], Malkov and Yashunin 2018,
https://arxiv.org/abs/1603.09320 (§4 structure, §6 deletion, §4.2.3 memory).

**Problem addressed:** ensuring one user's memories are never retrieved in another user's
session (requirement R16, constructed failure X3).

**Mechanism:** attach an owner or tenant identifier to every stored memory, and restrict
each retrieval so it only considers memories whose owner matches the querying user. Both
index families support restricting a search: FAISS scans only selected inverted lists
(§2), and both provide implementation-level ID selection.

**Evidence reported by the source:** FAISS establishes that a query need only scan a
subset of the database via the inverted-file structure (§2). Neither paper measures
isolation directly, since neither addresses multi-tenancy. The subset-search capability
is documented; the isolation use of it is not.

**Assumptions and limitations:** the index's own partitioning is by geometric similarity,
not by owner. FAISS colocates similar vectors in the same inverted list, and HNSW links
similar nodes directly to each other (§4). So the index actively groups the data that
isolation must keep apart, meaning correct isolation depends entirely on an owner filter
applied on top of the index, not on the index's structure.

**Component and failure mode affected:** component 10 (privacy/isolation), requirement R16,
failure X3 (cross-user leakage).

**Current approach:** retrieval ranks by similarity to the query with no owner constraint,
so a similar memory from another user can be returned. This is failure X3.

**Proposed change:** enforce an owner-ID filter as part of every retrieval, so only the
querying user's memories are eligible.

**Expected benefit:** eliminates cross-user leakage by construction, since another user's
records are never eligible for retrieval.

**Integration and operational cost:** low. Requires an owner ID on every memory at write
time and a filter clause at read time. Shifts a requirement onto the admission path (every
memory must be tagged with a correct owner), which links to R17.

**Security, privacy, reliability implications:** the guarantee depends on where the filter
is applied. Filtering during the search means other users' vectors are never examined.
Filtering after retrieval means their vectors were examined and then discarded, a weaker
guarantee. For HNSW specifically, filtering during traversal risks stranding the search in
a region of non-matching nodes and degrading recall, because search starts from a single
shared entry point (§4). This is the central design question, not a settled detail.

**Does the evidence transfer?** Partly. The subset-search capability transfers directly.
The isolation guarantee does not come from the papers; it is a system design decision
layered on top, so it must be validated in my own setup.

**Would something simpler work?** An alternative is a separate index per user, which gives
clean isolation and clean deletion with no filtering logic, at the cost of higher memory
overhead (60 to 450 bytes per object of index links, per user, §4.2.3) and loss of any
cross-user structure. This is a real alternative to weigh, not an obviously worse one.

**Decision: ADOPT (filtering by owner ID), with the during-versus-after-search question
carried to prototype.** Owner-ID filtering is the mechanism for R16. Whether it is enforced
during or after search, and whether a shared filtered index or per-user indexes is used,
must be settled by the prototype, because the isolation guarantee and the HNSW recall risk
depend on it.

**Revisit condition:** reconsider the shared-index approach if the prototype shows that
during-search filtering degrades recall unacceptably on clustered per-user data, in which
case per-user indexes become the preferred option.

## Idea 3: Hybrid detection at admission for sensitive data

**Source and citation:** Microsoft Presidio, https://github.com/microsoft/presidio
[practitioner tooling]. LangChain LLM Gateway redaction documentation,
https://docs.langchain.com/langsmith/llm-gateway-redaction [practitioner documentation].
Wavect, PII Redaction for LLM Prompts, 2026, https://wavect.io/blog/pii-redaction-before-llm-prompts/
[practitioner analysis]. Liu et al., Learning to Refuse, 2024,
https://arxiv.org/abs/2407.10058 [peer-reviewed, partial relevance only].

**Problem addressed:** preventing credentials, connection strings, API keys, and personal
data from being stored in memory during ordinary debugging (requirement R17, constructed
failure X4).

**Mechanism:** a deterministic filter applied at the admission boundary, before anything
is written to the store. Two detection layers: pattern-based rules for structured secrets
(API keys, tokens, connection strings), and a contextual NER model for unstructured
personal data. Detected values are either rejected or replaced with typed placeholders.
Presidio provides this as regex recognisers plus a spaCy NER backend, extensible with
custom recognisers.

**Evidence reported by the source:** LangChain's gateway documents detection of API keys,
tokens, and credentials across a range of provider formats, alongside Presidio-based
named-entity detection. Presidio is widely deployed and actively maintained. None of the
sources reports a measured recall or false-negative rate for this class of content.

**Assumptions and limitations:** the practitioner sources state plainly that no tool
guarantees complete detection, and that false negatives, task quality, and latency must
be evaluated on one's own data before production. Liu et al. independently report that
fine-grained separation of sensitive from benign content about the same entity is
unsolved. Detection of secrets is pattern-dependent, so novel or unusual credential
formats will be missed.

**Component and failure mode affected:** component 10 (privacy/isolation) and component 3
(extraction and admission), requirement R17, failure X4.

**Current approach:** none. Any information judged useful is eligible for storage, which
is precisely failure X4: in debugging, usefulness and sensitivity are correlated, so a
usefulness-based policy preferentially retains secrets.

**Proposed change:** insert a detection step at admission, before a memory is written.
Content flagged as a credential or secret is not stored. Personal data is either not
stored or stored with the value replaced.

**Expected benefit:** prevents the highest-severity items (live credentials) from ever
entering the store, which is a stronger guarantee than detecting them later, since
anything stored may be retrieved or injected into a later context.

**Integration and operational cost:** moderate. Adds a processing step to every write,
so admission latency increases. Custom recognisers must be written for the credential
formats common in my domain, since these are not standard PII entities.

**Security, privacy, reliability implications:** two failure directions, and they trade
against each other. Over-blocking rejects benign debugging content and degrades the
assistant's usefulness. Under-blocking stores a live secret. The second is far more
severe, which argues for tuning toward over-blocking. Detection also creates a false sense
of safety if treated as complete; the sources are explicit that it is not.

**Does the evidence transfer?** Partially. The architectural pattern transfers directly
and is well established. The detection accuracy does not transfer, because no source
reports rates for the specific content my domain produces (config files, stack traces,
connection strings pasted mid-debugging). This must be measured on my own data.

**Would something simpler work?** A pattern-only filter (regex for common key and
connection-string formats) with no NER would be simpler, faster, and would catch the
highest-severity cases. It would miss unstructured personal data. Given that credentials
are the dominant risk in this domain, a pattern-first approach may be sufficient for a
first implementation, with NER deferred. This is worth testing before adopting the full
hybrid.

**Decision: PROTOTYPE.** The admission filter is necessary, since R17 is a gated
requirement and failure X4 is otherwise unmitigated. But which detection approach to
commit to cannot be settled from the sources, because none reports accuracy on
debugging-style content. Build a minimal filter, assemble a small test set of realistic
pastes (config files, connection strings, stack traces, benign code), and measure both
failure directions before adopting.

**Success criteria:** no live credential in the test set is admitted, and benign
debugging content is admitted at a rate high enough that the assistant remains useful.

**Evidence that would falsify the proposal:** if pattern-based detection admits
credentials in realistic pastes at any meaningful rate, admission filtering alone is
insufficient and the design needs a second control (for example, treating all stored
content as sensitive by default rather than filtering selectively).

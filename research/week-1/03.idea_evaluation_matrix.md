# Week 1 - Idea Evaluation Matrix

## Idea 1: Machine unlearning as a deletion mechanism

**Source and citation:** Zhang et al., A Comprehensive Survey of LLM Unlearning, 2025.
https://arxiv.org/abs/2503.01854

**Problem addressed:** Removing the influence of specific data (personal, copyrighted,
or harmful) from a trained model, while preserving general performance and without full
retraining.

**Mechanism:** Adjust the weights of an already-trained model so the target data (the
"forget set") stops influencing outputs, while a "retain set" and general world knowledge
are preserved. Achieved through training-like procedures rather than deletion, because the
data is diffused across the parameters and has no single location to remove.

**Evidence reported by the source:** As a survey, it catalogs methods and their reported
trade-offs rather than presenting one result. It documents two consistent risk categories:
utility degradation (the model gets generally worse) and catastrophic forgetting (removing
one item damages related knowledge).

**Assumptions and limitations:** Assumes the data to be removed lives in the model's
weights, absorbed during training. Its cost and difficulty exist precisely because
parametric memory cannot be edited directly. Success is hard to guarantee and is measured
against the risk of collateral damage to retained knowledge.

**Component and failure mode affected:** Component 10, deletion requirement R4. Related
to the "right to be forgotten" the survey cites as motivation.

**Current approach:** Store memories in an external database, separate from the model.

**Proposed change:** None. Adopting unlearning would mean placing user memories into the
model's weights and then paying to remove them, which introduces the exact problem the
survey describes.

**Expected benefit:** None for my architecture. The legal requirement unlearning is
motivated by (deletion on request) is already satisfied by external storage.

**Integration and operational cost:** Very high if adopted, since it would require
fine-tuning user data into the model and running an unlearning procedure per deletion
request. By contrast, external deletion is a single database operation.

**Security, privacy, reliability implications:** Unlearning carries a risk of utility
degradation and catastrophic forgetting. External deletion carries neither, since removing
a record cannot degrade the model's general ability.

**Does the evidence transfer?** No. The evidence concerns removal from parametric memory.
My memory is non-parametric, so the difficulty the research addresses does not arise.

**Would something simpler work?** Yes. A database delete achieves the required outcome
(the memory is gone and no longer retrievable) at negligible cost, satisfying R4 and the
"right to be forgotten" directly.

**Decision: REJECT.** Unlearning solves removal from model weights. My architecture keeps
memory external and therefore deletable by ordinary operations, so unlearning addresses a
problem my design avoids. This also yields a design principle: do not fine-tune user
memories into the model, as doing so would forfeit trivial deletion and incur unlearning's
cost and risks.

**Revisit condition:** Reconsider only if the design ever moves user memory into model
parameters (for example, personalization via fine-tuning). While memory remains external,
this decision stands.
